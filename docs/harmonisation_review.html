0. Scope and method

Read in full (line by line): all 33 modules of modules/harmonisation/ (~29,300 LOC), the concordance/, shared/ and adapters/gwas2vcf/ sub-packages, config/models/modules/harmonisation.py, the 243 KB config/defaults/modules/harmonisation.yaml (149 policies across 22 groups, sampled programmatically), the supporting core/ modules it depends on (pipeline_logging, processes, paths, io/*, statistics, dataframes, vcf, values), pipeline/{registry,planner,executor,cli,runners}.py, and the 25 tests/test_harmonisation_*.py files plus test_architecture.py.

Method. Data flow was traced first — the dataset-level stage and the sixteen per-chromosome steps — before any judgement was formed about an individual step, because several of the findings below are ordering problems that are invisible when a module is read in isolation. Every candidate finding was then re-grepped across src/ to confirm it is not already compensated elsewhere; a number of candidates were discarded at that stage (noted in §7). The highest-severity findings were independently re-verified against the exact cited lines, and where behaviour depended on a numeric or library detail it was executed (sys.exit() status, np.float32 cast behaviour, YAML default extraction).

Confidence column. CONFIRMED = the code path was read end-to-end and does what the finding says. PLAUSIBLE = the code is as described, but the impact depends on a caller, a config value, or a third-party library behaviour that could not be fully resolved from the staged copy. Findings marked ✔ were additionally re-verified line-by-line during a second pass.

Staged-copy limitations (stated so nothing is over-claimed): postgwas/modules/qc_summary/, postgwas/modules/formatting/ and the top-level postgwas/cli/ package were not available; claims touching them are marked PLAUSIBLE. polars/pydantic were not installed, so nothing that requires them was executed.

1. What the module does — data flow

Understanding this order is a prerequisite for §3; several findings are ordering defects.

Dataset stage (service.run_harmonisation_pipeline)

validate_config (no file read)
  → validate_header (one line read)
  → read_summary_statistics (full eager parse; immutable source_snapshot cloned)
  → validate_content
  → resolve_duplicate_variants
  → study_properties.resolve_study_properties
        _decide_effect_type → _decide_pvalue_type → _decide_or_se_scale → _decide_eaf_is_maf
  → genome_build.infer_genome_build
  → preflight_harmonisation_resources           (before any worker starts)
  → chromosome_partition.write_chromosome_partitions
  → harmonise_chromosomes  ── ProcessPoolExecutor(spawn), retry rounds
  → concat_vcfs_by_build → post-merge QC (01..05) → cleanup → run manifest

Per-chromosome stage (service.process_one_chromosome, 16 steps)

# Module Effect on the statistics
01 pl.read_csv —
02 coordinates chr/pos normalisation, chromosome rename map, allele pattern checks
03 effect_type OR → ln(OR); SE := SE/OR iff se_scale=as_given
04 allele_frequency → strand on swap: β := −β, Z := −Z, EAF := 1−EAF; SE untouched
05 sample_size Neff = 4/(1/N_case + 1/N_ctrl)
06 effect_from_z fills whichever of BETA/SE is absent (Zhu reconstruction)
07 p_values scale detection (raw / −log10 / −ln), clip, flag
08 standard_error SE = \|β / Φ⁻¹(1−p/2)\| — only when no SE column exists at all
09 z_score Z = β/SE (or retains a supplied Z)
10 effect_validation the validation gate
11–13 imputation_quality, variant_identifiers, effect_validation.final_completeness_check
14–16 gwas2vcf_export → gwas2vcf_runner → vcf_processing TSV export, adapter, bcftools norm/annotate/csq/liftover

The ordering itself is correct on the three axes that usually break: OR→log(OR) precedes allele swapping; Neff exists before it is consumed; the exact SE = β/Z is attempted before the lossy SE-from-p; and Z is recomputed last so it can never be stale. The defects below sit inside steps, with the exceptions noted in F-19 and F-26.

9. Overall assessment

This is a substantially above-average harmonisation implementation, and considerably more careful than most tools in this space. Three things in particular are genuinely well engineered and are the reason the defects above are findable at all:

  1. The reject/provenance model. RejectCollector with fill_null(True) masking, exact keep/reject complements from a single partition_by, an unregistered-reason guard that raises, one-rejection-per-source-row enforcement, exact snapshot matching, and a reconcile() conservation law enforced as a hard error. Very few pipelines in this domain can tell you where a variant went.
  2. The refusal to guess. strand.py hard-fails without an EAF/MAF decision, without an effect-type decision, and refuses to orient odds ratios whose SE scale is unresolved. effect_type.py raises rather than assuming a log-odds scale. p_values.py refuses to guess between the two log scales. sample_size.py refuses a lone case count with the correct 2×–4× justification. These are exactly the right failure modes, and they are rarer than they should be.
  3. The policy registry. 149 policies with plain-English help, origin, typed validators rebuilt from spec, all problems reported at once, immutable and picklable for worker fan-out, and changed_from_default() recorded into both the log and the manifest.

The flip-vs-swap distinction is correct — the single most important thing in the module. Four orientations are enumerated explicitly, output alleles always come from the reference, and β/Z/EAF are transformed only on swap, with SE correctly left alone. A reverse_complement (non-swapped) match rewrites the allele letters without touching any statistic. That is right and should be preserved verbatim.

Where it falls short clusters into four patterns:

  • Safety nets that provably cannot fire. max_reject_fraction: 1.0 (arithmetically unreachable), the underflow mask in p_values.py (logically unreachable), the liftover failure gate measuring the wrong denominator, z_pval_concordance being algebraically vacuous for the studies it exists to police, and the palindromic ambiguity band using & where | is needed. Each of these looks like protection in code review and provides none at runtime.
  • Shipped defaults that contradict the file's own recommendations. max_reject_fraction (rec. 0.95), liftover_swap (rec. update_tags), chromosome.rename_map (rec. includes 25→XY, 26→MT), mlogp_max (rec. null, which disables the flag), af_discordance_action: warn, declaration_mismatch_action: warn, population_frequency_qc.on_error: warn. The recommendations are right; the defaults are not.
  • A provenance boundary at step 13. Everything before it is rigorously accounted; everything after it (TSV export → gwas2vcf → bcftools) asserts removed=0 while nine drop points in the adapter discard variants into a debug log that is never enabled. That boundary is where a wrong genome build or a chr1-vs-1 mismatch turns into a small VCF and a green run.
  • No resource governance and no resume. execution.memory_gb is accepted and never read; polars' thread pool is unbounded; peak memory is ~4× the parsed frame before any worker starts; and core/completion.py — a complete resume framework — has zero call sites while the CLI re-runs the entire dataset on any failure.

The test suite protects the orientation matrix very well and almost nothing else that matters: the Zhu reconstruction is guarded by a tautology, the log-scale p-value conversion is never exercised, reconcile() has no test, and the final VCF write is unverified.

Verdict: the science is sound in design and mostly sound in implementation. The risk is concentrated in detection — several genuinely dangerous conditions (transposed EA/OA, wrong build, wrong INFO scale, adapter failure) are individually plausible and are each guarded by a check that warns, cannot fire, or measures the wrong quantity. Fixing the twelve must-fix items below is mostly a matter of changing defaults and adding gates, not of rewriting science.
